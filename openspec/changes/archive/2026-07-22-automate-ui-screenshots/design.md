## Context

README 固定展示四张 macOS 应用窗口截图，但当前图片来自真实用户曲库和人工操作。应用启动时会读取用户主题、曲库和播放记忆，因此单纯用脚本启动并模拟点击无法保证内容、窗口尺寸和页面状态稳定。macOS 自带 `screencapture` 可以按窗口编号截图，但需要应用在渲染完成后向脚本提供可靠的窗口编号。

## Goals / Non-Goals

**Goals:**

- 一条本地命令构建并生成四张确定性 README 截图。
- 截图进程与用户真实曲库、主题和播放记忆隔离。
- 直接初始化目标页面状态，不依赖坐标点击或辅助功能脚本。
- 固定窗口内容尺寸，并在 SwiftUI 首次渲染完成后再截图。
- 自动维护 README 截图区块并校验输出文件。

**Non-Goals:**

- 不在 GitHub Actions 等无桌面会话环境中运行截图。
- 不提供用户可见的演示模式入口。
- 不改变普通启动的数据加载、持久化或播放行为。
- 不引入第三方截图、图像处理或 UI 自动化依赖。

## Decisions

### D1：用隐藏启动参数直接选择场景

应用解析 `--screenshot-scene`、`--screenshot-ready-file` 和 `--screenshot-store`。支持 `light-home`、`dark-home`、`light-queue`、`light-lyrics` 四个场景。场景在 `AppState` 初始化期间设置，避免页面出现后再点击导致动画和焦点不稳定。

替代方案是 AppleScript 或坐标点击，代码更少，但受窗口焦点、布局变化和辅助功能权限影响，故不采用。

### D2：截图模式使用隔离演示状态

截图模式从 `SampleData` 派生固定曲库，并为专辑生成确定性封面；播放上下文、队列、当前进度和歌词均由 fixture 设置。截图模式关闭应用状态持久化，并使用脚本传入的临时存储目录。普通启动继续走原有持久化流程。

### D3：应用主动报告窗口就绪

截图模式在窗口出现后设置固定内容尺寸 `1240 × 760`，置于屏幕中央并激活。等待短暂渲染稳定时间后，应用把 `NSWindow.windowNumber` 写入 ready 文件。脚本轮询 ready 文件并调用 `/usr/sbin/screencapture -l`，不需要额外窗口查询工具。

### D4：脚本负责完整编排和校验

`Scripts/update-screenshots.sh` 先调用 `Scripts/bundle.sh`，再逐场景启动 app、捕获窗口、关闭本次启动的进程。脚本验证 PNG 存在且尺寸达到最低要求，并用带标记的固定模板更新 README 截图区块。

## Risks / Trade-offs

- [首次执行可能缺少屏幕录制权限] → 截图失败时给出明确的系统设置提示，授权后重新运行即可。
- [不同显示器缩放比例导致像素尺寸不同] → 固定逻辑内容尺寸，只要求四张图片尺寸一致且达到最低像素尺寸，不绑定绝对 Retina 倍率。
- [SwiftUI 或封面绘制尚未完成就截图] → 应用在窗口配置后延迟写 ready 文件，脚本只在 ready 后捕获。
- [脚本异常退出遗留应用进程] → 使用 trap 仅终止脚本自己启动的 PID，并清理临时目录。
