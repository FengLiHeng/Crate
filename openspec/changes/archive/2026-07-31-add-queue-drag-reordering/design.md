## Context

待播面板由两个不同的数据源组成：插播分区映射 `manualQueue`，而“接下来”分区映射 `ctx.ids` 中 `ctx.pos` 之后的部分。`PlayerStore` 已将这两部分及 `ctx.originalIds` 写入播放记忆，因此排序操作只需通过状态层更新现有数组，无需新增持久化模型。

## Goals / Non-Goals

**Goals:**

- 为两个分区提供边界安全、可测试的分区内移动 API。
- 拖动过程中以歌曲 id 标识条目，避免数组索引变化导致移动错误。
- 保持当前歌曲、上下文位置和播放进度不变。
- 普通模式下保存用户调整后的有效上下文；随机模式下不改写 `originalIds`。
- 为无法使用指针拖动的用户提供等价的命名移动动作。

**Non-Goals:**

- 不支持插播与“接下来”之间跨分区拖动。
- 不支持把当前播放曲目拖入待播分区。
- 不新增队列持久化格式或撤销历史。

## Decisions

- `PlayerStore` 接收分区内源、目标索引并自行校验边界。视图不直接改写数组，确保拖动与无障碍操作共享相同语义。
- “接下来”的索引以分区相对索引传入，状态层再换算为 `ctx.pos + 1` 后的绝对索引，因而当前项和已播放前缀不会移动。
- 普通模式调整“接下来”后，将 `originalIds` 对齐新的当前有效顺序；随机模式只更新 `ctx.ids`，使关闭随机仍按既有 `originalIds` 恢复。
- SwiftUI 拖放状态携带分区和歌曲 id；目标行进入时按当前 id 重新解析索引并触发移动，从而在连续跨行拖动时避免陈旧索引。
- 队列行始终显示拖动手柄；首尾边界只暴露可执行的“上移”或“下移”无障碍动作。

## Risks / Trade-offs

- [SwiftUI 行级拖放在快速跨越多行时会连续触发] → 每次使用歌曲 id 重新定位，并让相同索引成为无操作。
- [大队列连续拖动会多次调度播放记忆保存] → 复用现有节流写入逻辑，最终顺序仍会落盘。
- [跨分区拖动可能进入另一分区的目标行] → 拖放委托校验分区，不接受跨分区移动。
