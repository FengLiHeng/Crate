## Context

`PlayerStore` 当前用 `manualQueue` 保存手动加入的歌曲，用 `ctx` 保存播放上下文；播放器实际顺序始终是 `manualQueue + ctx` 的后续部分。`QueuePanelView` 却把这两段真实连续的顺序拆成两个带标题的分区。此次改动只调整用户看到的队列结构和置顶反馈，不迁移播放记忆，也不改变插播结束后回到原上下文的状态机。

## Goals / Non-Goals

**Goals:**

- 用单一“接下来”标题展示当前曲目之后的完整实际播放顺序。
- 让“下一首播放”添加的歌曲立即出现在第一行，并通过短暂强调和 toast 双重确认。
- 保留懒加载、双击播放、手动队列移除、拖动排序和无障碍动作。
- 沿用现有暖白/石墨主题令牌；短暂反馈使用已有 `accentSoft`，不新增常驻徽标或颜色。

**Non-Goals:**

- 不合并 `manualQueue` 与 `ctx` 的内部数据模型。
- 不改变“加入待播清单”、立即播放、随机播放、循环播放或播放记忆语义。
- 不新增跨内部队列类型的拖动排序能力。

## Decisions

### D1：展示层拼接两类后续歌曲

`QueuePanelView` 仍分别读取 `manualQueue` 和 `upcomingIds`，但只渲染一次“接下来”标签，并按 `manualQueue` 在前、上下文后续在后的顺序连续输出行。这与播放器取下一首时的优先级完全一致，也避免数据迁移风险。

备选方案是把所有歌曲写入单一上下文队列。该方案会影响插播结束回归、随机模式原始顺序以及既有播放记忆，超出本次界面简化的范围。

### D2：用短生命周期状态标记最新置顶歌曲

`PlayerStore` 在成功执行 `playNextSong` 后记录歌曲 id，并在约 1.4 秒后自动清除；重复操作以最后一次 id 为准。对应队列行使用 `accentSoft` 进行一次克制的背景强调，系统开启“减少动态效果”时不依赖位移或缩放表达反馈。

视觉令牌完全继承现有主题：正文 `text`、次级文字 `text2/text3`、面板 `panelBg`、强调背景 `accentSoft`、强调描边/文字 `accent`。这次设计的唯一特征动作是新下一首落到列表顶部时的短暂色彩呼吸，其余行保持安静。

### D3：保留内部类型对应的行能力

手动队列行继续提供移除按钮并调用 `playManualAt`；上下文行继续调用 `playContextAt`。两类行在视觉上组成一个列表，但排序仍在各自内部序列中进行，以免一次 UI 简化隐式改写播放上下文。

## Risks / Trade-offs

- [合并展示后用户看不到手动队列与上下文边界] → 这是刻意移除的内部概念；播放顺序、移除按钮与操作结果仍保持明确。
- [拖动不能跨越内部边界] → 当前版本维持既有约束；队列仍按实际顺序展示，后续若需要完全自由排序应另立状态模型变更。
- [延迟清除反馈状态可能与连续操作竞争] → 清除闭包仅在 id 仍等于本次记录时生效，避免旧任务清除新反馈。
