## Context

Crate 当前的播放状态由 `PlayerStore` 维护，底部播放条通过 `currentSong`、`progress` 和 `seek(to:)` 暴露播放进度与跳转能力。导入流程已经支持同目录同文件名图片作为封面 sidecar 文件，且不把用户原始文件复制进应用目录。

歌词功能应沿用这个本地文件模型：音频文件旁存在同名 `.lrc` 时才开放歌词页；歌词内容按需读取和解析，不进入曲库 JSON。这样用户导入歌曲后补放 `.lrc` 文件也能生效，并避免新增迁移、同步和存储复杂度。

## Goals / Non-Goals

**Goals:**

- 从当前播放歌曲的真实文件路径推导并读取同名 `.lrc` 文件。
- 支持常见标准 LRC：`[mm:ss]`、`[mm:ss.xx]`、同一歌词多时间戳、`[offset:+/-毫秒]`。
- 在播放条封面点击后打开歌词播放动态页面；无法打开时显示明确 toast。
- 歌词页根据播放进度高亮当前行并自动滚动，切歌、seek、暂停/播放后状态保持同步。
- 点击歌词行可跳转到对应播放时间。
- 用单元测试覆盖解析器核心边界。

**Non-Goals:**

- 不联网搜索、下载或匹配歌词。
- 不支持逐字歌词、翻译歌词、双语歌词、LRCX 扩展或卡拉 OK 分词高亮。
- 不把歌词内容持久化进 `library.json`，也不维护歌词缓存目录。
- 不提供歌词编辑、偏移手动调节或另存歌词能力。
- 不改变播放队列、随机/循环、失效曲目跳过等播放状态机语义。

## Decisions

1. **歌词文件作为音频 sidecar 懒加载**

   通过 `song.fileURL?.deletingPathExtension().appendingPathExtension("lrc")` 查找歌词文件，点击入口时现场检测文件是否存在并读取。相比导入时扫描歌词，这更符合用户截图里的文件组织方式，也允许用户后续补齐歌词文件而不用重新导入歌曲。

   备选方案是在导入时记录 `lyricsURL` 或 `hasLyrics`。放弃原因是该状态容易和磁盘文件变化失真，还会增加持久化兼容负担。

2. **新增纯 Swift LRC 解析器**

   新增独立解析类型，例如 `LRCParser`、`LyricLine`、`ParsedLyrics`。解析器只依赖 Foundation，输入 `String`，输出按时间升序的歌词行数组和可选元信息。时间戳解析支持分钟、秒和 0-3 位小数；`offset` 以毫秒应用到每一行时间，最终时间不小于 0。

   备选方案是引入第三方 Swift 歌词库。当前需求范围很小，项目也没有外部依赖；自研解析器更容易测试和维护。

3. **读取编码采用保守兼容策略**

   首选 UTF-8 读取；失败时再尝试 UTF-16、UTF-16LE、UTF-16BE，以及系统默认字符串解码。读取失败或解析后没有任何有效时间行时视为歌词不可用，toast 提示“歌词文件无法解析”。

   备选方案是只支持 UTF-8。很多本地 `.lrc` 文件来自旧工具或 Windows 环境，编码可能不是 UTF-8；增加少量 fallback 可以显著降低误判。

4. **歌词页状态归 `AppState` 管理，播放时间仍由 `PlayerStore` 驱动**

   `AppState` 增加歌词页打开状态和当前解析结果，例如 `lyricsSheet` 或 `lyricsPage`。页面不保存自己的播放进度，而是每次从 `app.player.progress` 推导当前行。当前歌曲变化时，如果歌词页仍打开，应尝试为新当前歌曲刷新同名歌词；刷新失败则关闭歌词页并 toast，避免显示上一首歌的歌词。

   备选方案是让歌词页自己监听文件和播放器。放弃原因是 Crate 当前把全局 UI 状态集中在 `AppState`，继续集中管理更一致，也更容易处理 toast 与关闭行为。

5. **歌词页作为主区域覆盖层，底部播放条保留**

   在 `RootView` 的主内容区域上承载 `LyricsPlaybackView`，覆盖侧边栏/资料库/队列区域，但不覆盖底部播放条。页面提供返回按钮或关闭按钮回到原资料库状态。这样用户进入动态歌词后仍能使用底部播放控制、进度条和音量。

   备选方案是新开窗口或 sheet。放弃原因是歌词播放是沉浸式播放状态，不是临时表单；新窗口也会增加焦点和快捷键处理成本。

6. **当前歌词行用二分定位，滚动做节流**

   解析结果按时间排序后，页面根据 `progress` 二分查找最后一个 `time <= progress` 的行。当前行变化时用 `ScrollViewReader` 滚动到该行。为了避免进度计时器频繁触发布局，只有当前行 id 变化时滚动，不按每个 progress tick 滚动。

   备选方案是每次渲染线性扫描。歌词行数量通常不大，但二分实现简单，可以避免长歌词或高频刷新时产生不必要开销。

7. **点击歌词行复用现有 seek**

   每一行带时间戳的歌词可点击，点击调用 `app.player.seek(to: line.time)`。如果当前没有歌曲或播放器状态已失效，按钮不执行额外逻辑；继续遵循 `PlayerStore.seek(to:)` 的边界裁剪。

## Risks / Trade-offs

- [Risk] 本地 LRC 文件编码复杂，仍可能读取失败。→ Mitigation: 提供多编码 fallback；失败时 toast 清晰提示，不影响播放。
- [Risk] 歌词页打开期间用户切歌，旧歌词短暂显示。→ Mitigation: 以当前歌曲 id 作为歌词页内容身份，currentId 改变时刷新或关闭。
- [Risk] `.lrc` 时间戳不准或文件含非标准扩展标签。→ Mitigation: 首版只承诺标准 LRC；非标准内容跳过或按普通文本忽略。
- [Risk] 自动滚动和用户手动滚动冲突。→ Mitigation: 首版始终跟随当前行；后续可增加“手动滚动后暂缓跟随”的高级交互。
- [Risk] 点击封面入口不够可发现。→ Mitigation: 增加 hover/指针反馈和 help 文案；无歌词时使用 toast 说明缺少同名 `.lrc`。

## Migration Plan

1. 新增 LRC 解析模型和解析器，不改变现有持久化模型。
2. 在 `AppState` 增加同名歌词查找、读取解析、打开/关闭歌词页和切歌刷新逻辑。
3. 在 `PlayBarView` 当前歌曲封面上增加点击入口和 hover/help 反馈。
4. 新增 `LyricsPlaybackView`，复用现有 `CoverView`、主题 token 和 `PlayerStore` 控制能力。
5. 为解析器添加 SwiftPM 单元测试，覆盖多时间戳、offset、无效行、空歌词和排序。
6. 运行 `swift build`、相关测试和 `Scripts/bundle.sh`，手动验证有歌词、无歌词、解析失败、切歌、seek 和重启后补放 `.lrc` 的行为。

## Open Questions

- 歌词页是否需要键盘快捷键退出（例如 Esc）可以在实现时按现有窗口快捷键风格决定；不是首版阻塞项。
- 是否需要在歌曲表格或播放条提前显示“有歌词”标识暂不纳入首版，避免增加列表扫描成本。
