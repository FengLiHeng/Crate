## Context

当前资料库数据集中在 `AppState.albums`、`AppState.library` 和 `AppState.playlists`，通过 `PersistedLibrary` 写入 `library.json`。单曲删除已经会从资料库、分组引用、插播队列和播放上下文中移除对应歌曲；失效曲目批量清理也复用了类似路径。

待播清单由 `PlayerStore.manualQueue` 与 `PlayerStore.ctx` 共同派生：`clearQueue()` 只清空插播和当前曲目之后的上下文，保留当前播放。清空歌曲列表需要更强的语义，必须停止当前播放并重置整个播放会话。

## Goals / Non-Goals

**Goals:**

- 提供受确认保护的一键清空歌曲列表入口。
- 清空全部歌曲、专辑、失效曲目标记和分组内歌曲引用，并持久化结果。
- 保留分组容器，方便用户清空后继续使用已有整理结构。
- 停止当前播放并清空插播队列、播放上下文和待播清单展示。

**Non-Goals:**

- 不删除用户磁盘上的原始音频文件。
- 不删除分组容器、不重命名分组、不改变分组排序。
- 不改变现有“清空待播清单”按钮语义；该按钮仍保留当前播放。
- 不新增自动撤销或回收站能力。

## Decisions

### D1. 在 `AppState` 聚合清空资料库

新增 `clearLibrary()` 作为唯一入口，由它协调 `albums`、`library`、`playlists`、`missingIds`、`view`、`selectedId` 和播放器状态。这样可以让持久化、索引重建和 UI 状态收敛在应用状态层，避免视图层直接操作多个数据结构。

备选方案是视图按钮分别清空多个属性，但这会把业务顺序暴露到 UI，后续容易遗漏播放器或分组引用。

### D2. 在 `PlayerStore` 提供播放会话重置

新增 `resetPlaybackSession()`，内部停止引擎、清空 `manualQueue`、重置 `ctx`、清掉 `isManual` 和跳过记录。它和现有 `clearQueue()` 分工明确：前者用于曲库级清空，后者用于面板里的待播清单清空。

备选方案是对所有歌曲逐个调用 `handleSongRemoved(_:)`，但大量歌曲时会重复调整上下文，并且语义不如一次性重置清晰。

### D3. 保留分组容器但清空歌曲引用

清空歌曲列表后，`playlists` 数组仍保留名称和排序，只将每个分组的 `songIds` 置空。这样用户可继续使用已有分组结构导入新歌曲，也不会留下指向旧歌曲的悬空引用。

备选方案是删除所有分组，使状态完全回到首次启动；但用户明确需求是清空歌曲列表，不是清空组织结构。

### D4. UI 使用危险按钮和确认弹窗

入口放在歌曲列表头部工具区，使用垃圾桶图标和确认弹窗。仅在资料库非空时启用，确认文案明确该操作会清空歌曲列表和待播清单，但不会删除磁盘文件。

## Risks / Trade-offs

- [误触清空] → 使用确认弹窗，并将按钮设计为危险操作。
- [分组保留造成“空分组”增多] → 这是有意取舍，保留用户整理结构；用户仍可通过现有分组管理删除不需要的分组。
- [持久化触发多次] → 清空操作会更新多个 `didSet` 属性；数据量较小时可接受，后续若需要可引入批量持久化抑制机制。
