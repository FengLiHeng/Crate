## Context

当前导入流程集中在 `AppState.importFiles` 与 `parseMetadata(url:)`：导入前用 `AVAudioPlayer` 校验可解码，随后通过 `AVURLAsset.commonMetadata` 读取标题、艺术家、专辑名与时长，并创建 `Song` 与可选 `Album`。曲库通过 JSON 编码持久化到 Application Support，启动时直接解码 `PersistedLibrary`。

当前 UI 的封面渲染由 `CoverView(album:size:radius:)` 负责。它只接收 `Album?`，有专辑时显示基于专辑稳定散列色相生成的渐变，无专辑时显示默认渐变加音符图标。歌曲列表、播放条和队列面板都复用该组件，因此封面能力应通过共享组件扩展，避免每个视图重复处理图片/占位符逻辑。

## Goals / Non-Goals

**Goals:**

- 导入歌曲时读取音频文件内嵌专辑封面；若没有内嵌封面，则读取同目录同文件名图片作为封面，并随曲库持久化。
- 歌曲列表标题列优先显示真实封面；没有封面或封面解析失败时显示现有风格一致的占位符。
- 旧版 `library.json` 中没有封面字段的数据可以继续读取。
- 已导入但缺封面的历史歌曲，在启动时可从同名图片回填封面，避免用户必须清空重导。
- 保持封面渲染入口集中，后续播放条、队列面板等位置可复用同一逻辑。

**Non-Goals:**

- 不从网络下载封面，不根据专辑名或艺人名补全外部图片。
- 不新增专辑详情页、封面编辑或手动替换封面能力。
- 不改变导入入口、去重规则、播放流程或分组行为。
- 不要求迁移历史已导入歌曲重新扫描封面；历史歌曲可继续显示占位符，除非用户重新导入或未来新增重扫能力。
- 不批量重扫音频内嵌元数据；历史歌曲只做轻量同名图片回填。

## Decisions

1. 在数据模型中保存封面原始图片数据的轻量描述。

   为歌曲或专辑增加可选封面字段，例如 `artworkData: Data?` 与 `artworkContentType: String?`。字段保持 optional，使旧 JSON 解码可以自然兼容。真实图片仍由 SwiftUI 渲染层按需转换为 `NSImage`/`Image`，避免在持久化模型里保存平台 UI 类型。

   备选方案是只保存封面文件路径或把封面拆到独立缓存目录。当前应用规模较小，曲库 JSON 已是单文件持久化；直接 Codable 保存可减少文件生命周期管理。若后续曲库变大或封面体积成为问题，再拆分缓存目录。

2. 优先把封面挂在 `Album`，必要时从 `Song` 回退。

   导入元数据已有 `albumId` 与 `findOrCreateAlbum(title:artist:)`，同一专辑的多首歌曲共享一个封面更符合用户预期，也避免重复保存相同图片。导入时如果文件包含封面且创建或找到对应 `Album`，应把该封面记录到专辑；已有专辑没有封面时可补写，已有专辑已经有封面时保持现有封面稳定。

   对没有专辑名但有内嵌封面的文件，可在 `Song` 上保存歌曲级封面，避免为了封面强行创建“未知专辑”。渲染时优先级为：歌曲级封面、所属专辑封面、占位符。

3. 继续使用 AVFoundation 读取封面元数据，并支持同名图片回退。

   `parseMetadata(url:)` 已经通过 `AVURLAsset.commonMetadata` 异步读取通用元数据。封面应在同一遍 metadata 遍历中读取 `.commonKeyArtwork`，优先使用 `dataValue`，并记录可用的 MIME/content type。解析失败、数据为空或图片无法初始化时不阻断导入，只走占位符。

   当音频文件没有内嵌封面时，导入逻辑 SHALL 尝试读取同目录同 basename 的 `.jpg`、`.jpeg`、`.png`、`.webp` 图片。sidecar 图片是文件级来源，应保存到 `Song.artworkData`，避免同专辑多首歌因共用 `Album` 而互相覆盖。

   备选方案是引入专门的标签解析库。当前需求只需要内嵌封面与已有常规元数据，AVFoundation 覆盖面足够，避免新增依赖和打包复杂度。

4. 扩展 `CoverView`，让占位符和真实图片共享同一组件。

   将 `CoverView` 从只接收 `Album?` 扩展为可接收 `Song?` 与 `Album?`，或接收一个轻量 `ArtworkSource`。组件内部先尝试渲染真实图片，失败时走现有渐变占位符。歌曲表格先使用该扩展能力，播放条和队列面板可以在同次实现中一并改用，保持视觉一致。

   占位符继续使用现有渐变和音符图标，不引入新的视觉语言。这样没有封面的歌曲仍与当前界面风格一致。

5. 持久化兼容采用 optional 字段与容错解码。

   `Album`、`Song` 新增 optional 字段后，Swift 合成 `Codable` 通常可以读取缺失字段。实现时仍需要确认旧 `library.json` 能成功解码；如果合成解码因新增结构体嵌套导致失败，应为相关模型提供自定义 `init(from:)`，缺失封面字段默认 nil。

6. 对历史曲库执行轻量 sidecar 回填。

   启动加载持久化曲库后，遍历已有导入歌曲；如果歌曲没有 `artworkData` 且真实文件路径旁存在同名图片，则把图片保存为歌曲级封面并触发一次持久化。该迁移只读取同名图片，不重新解析所有音频文件元数据，避免启动成本不可控。

## Risks / Trade-offs

- 封面图片过大导致 `library.json` 变大 → 导入时可限制保存数据尺寸或在实现中对超大图片跳过/压缩；首版至少应避免解析失败影响导入。
- 多首歌同专辑但内嵌封面不同 → 已有专辑封面保持稳定，只在专辑缺封面时补写；歌曲级封面用于无专辑场景。
- SwiftUI 列表频繁把 `Data` 转图片可能带来开销 → 在 `CoverView` 内保持逻辑简单，必要时增加小型解码缓存；当前缩略图尺寸很小，先不引入复杂缓存。
- 旧持久化文件兼容遗漏会导致启动空库 → 实现后必须用无封面字段的旧 JSON 或现有曲库文件验证启动解码。

## Migration Plan

1. 为 `Album` 与必要的 `Song` 增加 optional 封面字段，保持缺失字段解码为 nil。
2. 在导入元数据解析中读取 `.commonKeyArtwork`，没有内嵌封面时读取同名图片，并写入专辑级或歌曲级封面字段。
3. 扩展 `CoverView` 渲染真实封面，失败时回退现有占位符。
4. 启动时为已有曲库中缺封面的歌曲回填同名图片封面。
5. 更新歌曲表格、队列面板和播放条调用点，传入歌曲与专辑上下文。
6. 运行 `swift build` 与 `Scripts/bundle.sh`，并手动验证有封面/无封面文件导入和重启后显示。

## Open Questions
